## Production trace and inventory

Both the file picker and public URL reach `loadArchive()`. It calls `openGameArchive()`, decodes the ZIP with `readArtifacts()`, builds references, identifies the embedded GAM, and builds the opening scene. The scene snapshots the resolved board, TEM, tiles and walking ANMs, collision, placements and activation polygons. The player mounts on that scene, dispatches placed and BRD scripts and GAM keys, and passes interpreter outcomes to the fight and transfer bridges. The viewer also has a separate inspector/export path that can use an externally uploaded Main File. ## Why both source projections belong inside compatibility

### Dialogue projection

- **Reads from source.** The GAM startup binding and its rooted include graph supply literal numeric assignments, scanned lexically with bounds and conflicting constants removed. This can collect assignments inside branches or method bodies that never ran. Support requires `maxclues` and `itemtalkthreshold`. Each candidate placed PRG must resolve includes declaring `setTxt` and `updateClues`. The compiler extracts literal text, portrait-derived speaker names, frozen segments, the first/repeat control shape, indexed visits, clock variable names/threshold, a one-time opening assignment, and an optional flag inferred by searching the helper. [tk3-source-dialogue.mjs:45–113](https://github.com/jmbjr/rpgtk_godot/blob/fb82939aa4f22229475912ca62c2271d0a672653/tk3-source-dialogue.mjs#L45-L113) · [tk3-source-dialogue.mjs:129–170](https://github.com/jmbjr/rpgtk_godot/blob/fb82939aa4f22229475912ca62c2271d0a672653/tk3-source-dialogue.mjs#L129-L170) · [tk3-source-dialogue.mjs:193–289](https://github.com/jmbjr/rpgtk_godot/blob/fb82939aa4f22229475912ca62c2271d0a672653/tk3-source-dialogue.mjs#L193-L289)
- **Supplies behavior.** The projection chooses messages and owns the clock and visit gate. It interprets a specific static shape, ignores allowed visual/setup statements as effects, and preselects the first/repeat pages. A matching opening `playerLocation` and same-board `Send` are validated as a recognizable pair and skipped at runtime. It does not execute the helper bodies, evaluate their branches or implement general arrays, methods, timers, object dispatch or message windows. [tk3-source-dialogue.mjs:173–191](https://github.com/jmbjr/rpgtk_godot/blob/fb82939aa4f22229475912ca62c2271d0a672653/tk3-source-dialogue.mjs#L173-L191) · [tk3-source-dialogue.mjs:205–289](https://github.com/jmbjr/rpgtk_godot/blob/fb82939aa4f22229475912ca62c2271d0a672653/tk3-source-dialogue.mjs#L205-L289) · [tk3-source-dialogue.mjs:310–350](https://github.com/jmbjr/rpgtk_godot/blob/fb82939aa4f22229475912ca62c2271d0a672653/tk3-source-dialogue.mjs#L310-L350)
- **Writes and precedence.** The statement allowlist accepts some scalar assignments/increments and visual calls whose effects the projection never applies. Dialogue claims Talk for a matched placement before the ordinary placed PRG path. The separate paraphrased fallback uses its own inn state and clock. ### Menu projection

- **Reads from source.** The GAM action supplies the entry PRG. The recognizer looks for an include and a no-argument call, resolves one include, looks for a free method with the call's name, then extracts numeric switch cases with `checked[event] == 0`, `clues++`, `updateClues("literal")` and a visit increment. It reads `SIDEMENU` labels from text or `mm*_inactive` graphics, `PROFMENU` profiles from startup arrays, a cancellation check against `-1`, and a helper-derived terminal flag. The literal method name is variable, yet the semantics assume BSTW's CCmap/clue conventions. ## Boundary for integration review

1. **Three explicit launch modes.** Primary **Play game** takes the archive-owned context through bounded GAM startup, or opens the bound scene when startup is empty. **Play opening board (direct)** is a diagnostic command that visibly bypasses startup and starts a fresh generic session. Compatibility is an opt-in under a neutral Compatibility control. Selecting the named BSTW mode is the first point at which adapter code loads and eligibility runs. Eligible title **New** starts a fresh adapter-backed session. A rejection stays inside that control and leaves generic play selectable. Mode is scoped to the loaded archive and cleared when another ZIP opens.
2. **Eligibility and activation are separate.** Use the existing BSTW GAM 2.9 and verified title/New evidence for profile eligibility: the title and GAM startup/board/TEM bindings, rooted title script plus its source signatures and supported opening scene for New. Show art availability independently as a fallback status. An archive hash is evidence for local regression, while runtime eligibility is checked from decoded bindings and source so an eligible diagnostic copy can work. Names, lookalike script shapes, and successful parsing alone cannot activate a profile. The selected profile grants claims only after the per-binding checks below.
3. **Claim individual source bindings.** Verify the archive root, main and canonical opening board for projected interactions. Use the audited six ordinary clue-bearing placement PRGs and the opening `mwinStartBoardLoad.prg` from #92, matching the selected resolved placement and its expected BRD or ITM binding. Bind the approved cases to their source provenance and keep synthetic fixture selection in test code. Resolve the unique valid BRD inn override to the approved `mwininn.prg` binding before permitting the paraphrased fallback. Compile source dialogue for that same target first. Verify the menu entry through the actual GAM action and rooted `menuMain.prg → menus.prg::MainMenu` binding. The cutover covered those bindings. The scoped Q extension is specified in [BSTW browser ending](bstw-browser-ending.md). Moved or erased targets go through the same generic visibility and same-layer selection. Outside the approved capabilities, use the ordinary interpreter and its diagnostics. [Prior BSTW binding audit](https://github.com/jmbjr/rpgtk_godot/blob/fb82939aa4f22229475912ca62c2271d0a672653/docs/specs/bstw-ending-plugin-audit.md#L29-L85)
4. **Own only compatibility UI and game-rule state.** The adapter owns title, clue/menu/dialogue plans, cooldowns, fallback inn state, messages, its controls and DOM cleanup. The player owns neutral input, board drawing, render lifecycle and the common effect driver. The generic script session owns interpreter variables, context, wait/continuation, encounter and erased items. BSTW-owned clue state is initialized only by adapter New. Where an approved projection needs to communicate a source variable, apply a narrow patch of the variables it actually wrote to the live script store. Read current values for shared variables when needed. Avoid copying a second whole variable map over later script writes. Retain projected final-flag effects as data from the existing clue flow. Leave new ending execution to its own work.
5. **Preserve launch mode through a session lifecycle.** The host holds the selected archive context, launch mode and a factory for fresh state. Send preserves the active session and adapter instance. Reset and the fallback Game Over restart recreate that mode from its opening board and discard session effects. A configured defeat PRG runs through the normal effect driver and continues on the active board unless its own supported effect moves it. A compatibility restart after New returns directly to a fresh New session, with the title available through the explicit entry again. Closing play destroys the mount and controls. An explicit subsequent launch initializes its own state. Neither diagnostic launch nor generic Play activates compatibility.
6. **Keep browser fidelity limits visible.** Normal startup order and GAM key and defeat dispatch are supported where the browser has implemented the instructions and format. Board entry PRGs, startup-created players/boards, native menu UI, conditional or step-on item activation, broader movement fidelity and DLL combat need their own support. Keep both fight outcomes labeled test-only. Native Toolkit starts its selected actor, runs GAM startup, then opens the configured board when appropriate. It also runs board-enter RPGCode and uses the configured activation key and collision base, so those remain bounded-browser fidelity limits.
